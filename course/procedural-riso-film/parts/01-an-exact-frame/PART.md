# Part 01 — An Exact Frame: Repository Contract and Inspection Harness

A browser animation can look right every time you press Play and still be impossible to
reproduce, inspect at an exact moment, or export without dropped frames. This repository treats
every work as something stricter than an animation: a **function from time to pixels** that its
tools can call at any `t`, in any order, and get the same picture every time.

In this Part you make the smallest possible work of that kind: warm paper and one flat mark that
crosses it in one second. It will not look like a risograph print yet; that starts in Part 02.
What you are building is the thing every later Part stands on: a frame you can reproduce exactly,
a mental model of how the tools reach it, and evidence of what those tools can and cannot tell
you.

**You will make**

- `work/first-frame/`: a one-second film generated by the repository's scaffold, with one mark
  whose position is computed from `t`; a native 1080 × 1080 PNG of one exact frame; a 30-frame MP4.
- `work/stateful/`: the same film animated the ordinary way, kept as evidence of why that fails.
- `work/probe-720.html`: a copy of the supplied backing-store probe at a smaller backing store.
- `work/NOTES.md`: your written account of what each check establishes and what it does not.

**Supplied:** `project/backing-probe.html`, a short page used in the backing-store experiment.
Everything else you generate or write yourself.

## 2. Read the smallest contract

Start with how the repository describes itself. In the root [`README.md`](../../../../README.md),
read *How they're made*; its key sentence is "Every frame is a pure function of time
(`seek(t)`), so any moment can be inspected exactly and the MP4 cannot drop frames." In
[`CLAUDE.md`](../../../../CLAUDE.md), read the first paragraph and, under *Invariants*, the first
bullet and the first sentence of the second. The rest of that list belongs to later Parts.

Now open [`tools/fixture/index.html`](../../../../tools/fixture/index.html). It is under 50 lines and
is the repository's minimal working implementation of the contract every tool relies on. Read it
with these questions and write short answers in your notes:

1. The canvas has two sizes. Where is each one set, and what is each one?
2. List everything `render(t)` reads. Does anything it reads come from a previous call?
3. What is the first thing `render(t)` does to the canvas? What would a cold jump to `t = 2`
   show if that line were missing and you had just been looking at `t = 0.5`?
4. Where is the animation loop?
5. What does `window.__riso` expose?

The last two answers are the point of the file. There is **no loop**: nothing draws the fixture
until something calls `seek(t)`, and `seek` *is* `render`. The object on `window.__riso` is the
entire interface between a work and the tools:

| Field | Meaning |
|---|---|
| `duration` | Length in seconds. Tools sample within `0..duration`. |
| `ready` | `false` until the work has finished any preparation; tools wait for `true`. |
| `seek(t)` | Draw exactly the frame at time `t`, **synchronously**: finished when it returns. |
| `renderAudio`, `marks`, `shots` | Optional. The sound and editing halves of the contract; they appear in much later Parts. Ignore them for now. |

Now read how the tools use it. In [`tools/lib/browser.mjs`](../../../../tools/lib/browser.mjs),
read `openFilm` and `frameAt` (the first 60 lines) and answer:

6. What does a tool wait for before it touches the work, and for how long?
7. What happens to a request for anything that is not a local file?
8. The viewport is 720 CSS px but `deviceScaleFactor` is `size / css`. Why? (The comment in
   `openFilm` answers it.)
9. `frameAt` calls `seek(t)` and then immediately takes a screenshot. What would the screenshot
   contain if `seek` only *scheduled* drawing for later?

Then read the contract section of [`tools/README.md`](../../../../tools/README.md#the-contract).
Its sentence "a cold jump to `t` matches arriving there by playback" is what this Part is about.

Run the two tools this Part is built around on the fixture:

```sh
node verify.mjs fixture/index.html
node still.mjs fixture/index.html --at 1 --out $OUT/fixture.png
```

`verify.mjs` runs in Chromium and then Firefox. For each engine it prints the duration, a short
hash per inspected time, and a line comparing Firefox's frames with Chromium's. It ends with
`seek is pure in t; contract holds`. `still.mjs` prints `1080x1080 native PNG, repeatable` and a
sha256. You will learn what each of those phrases actually guarantees in the next sections.

Two things in the map deserve a sentence each in your notes. `render` is called from two places:
the player's `tick`, in playback order at whatever wall-clock time the browser has reached, and
`seek`, at whatever `t` a tool or the scrubber asks for, in any order. And `render` starts every
frame by resetting the context and drawing the whole paper, so nothing from the previous frame
survives: not pixels, not a transform, not an alpha.

## 4. One mark, one exact frame

Replace the empty `drawArt` with one plain Canvas mark:

```js
function drawArt(t) {
  ctx.fillStyle = INK.blue;
  ctx.beginPath();
  ctx.arc(300, 540, 90, 0, Math.PI * 2);
  ctx.fill();
}
```

`INK` is the scaffold's palette table and `ctx` is the page canvas's context. This is a flat RGB
fill, which is **not** how the repository puts ink on paper; Part 02 replaces it. Reload Firefox
to see it.

Export the frame at `t = 0.5` twice, in two separate runs:

```sh
node still.mjs $PART/work/first-frame/index.html --at 0.5 --out $OUT/static.png
node still.mjs $PART/work/first-frame/index.html --at 0.5 --out $OUT/static-again.png
```

Both runs print the same dimensions and the same sha256: two browser launches, two page loads,
two paper bakes, byte-identical files. Now read [`tools/still.mjs`](../../../../tools/still.mjs)
(20 lines) and write down exactly what its word "repeatable" checked. (It draws `t`, seeks
somewhere else, draws `t` again and compares the two captures. That is one detour, not a proof.)
Note also *how* it captures: `canvas.toDataURL()`, the canvas's own backing pixels, which no
window size or zoom level can change.

Run the contract check:

```sh
node verify.mjs $PART/work/first-frame/index.html
```

It passes, and within each engine every inspected time has the same hash, because the picture
does not change with `t`. Answer in your notes: **if your mark were supposed to move but you had
forgotten to use `t` at all, would `verify.mjs` notice?** Look at what it compares before you
answer. It checks that each time always produces the same pixels; it never checks that different
times produce the *right* pixels.

## 5. Make it move: the ordinary way

Now make the mark cross the paper in one second. Before writing it the repository's way, write
it the way most browser animation is written, so you can see what that costs.

Keep this version separately so you can compare it later:

```sh
mkdir -p $PART/work/stateful
cp $PART/work/first-frame/index.html $PART/work/stateful/index.html
```

In `work/stateful/index.html`, replace `drawArt` with the usual delta-time idiom: keep the
position in a variable, work out how much time has passed since the last frame, advance by
speed × elapsed time, and guard against a huge step after a stall.

```js
let markX = 160, lastT = 0;             // carried from one call to the next
function drawArt(t) {
  const dt = Math.min(t - lastT, 1 / 20); // the usual guard against a long stall
  lastT = t;
  markX += 700 * dt;                      // 700 px per second
  ctx.fillStyle = INK.blue;
  ctx.beginPath();
  ctx.arc(markX, 540, 90, 0, Math.PI * 2);
  ctx.fill();
}
```

This is careful code by ordinary standards: time-based rather than frame-counted, so it runs at
the same speed on a 60 Hz and a 144 Hz display, and protected against a tab that was asleep.
**Write down your prediction** of where the mark will be at the end of playback, and whether the
tools will accept this film. Then observe, in this order.

**In Firefox.** Press Play. Press Replay. It looks right both times: the mark crosses the paper
and stops near the right edge. Now click the scrubber *track* (not the thumb) near its right end, so the
time label jumps to about 0.90 in one step. Where is the mark? Press Replay again and watch the
whole second.

**With the tools.** Take the frame at `t = 0.6` two ways: on a fresh page, jumping straight to
0.6; and on a fresh page, seeking every 1/30 s from 0 up to 0.6, the way playback arrives there.

```sh
node shoot.mjs $PART/work/stateful/index.html --times 0.6 --engine firefox --out $OUT/stateful-cold
node shoot.mjs $PART/work/stateful/index.html --range 0:0.6:0.0333333333 --engine firefox --out $OUT/stateful-played
```

`shoot.mjs` writes one PNG per time into its `--out` folder. Open
`stateful-cold/t_000.600.png` and `stateful-played/t_000.600.png` side by side. They claim to be
the same moment of the same film.

Then run the contract check and read every line of its output:

```sh
node verify.mjs $PART/work/stateful/index.html
```

In the two PNGs the cold jump leaves the mark near the left edge (around x = 195) while the

`verify.mjs` prints `FAIL` lines of three kinds for the inspected times (`not repeatable`,

Explain each observation in your notes, in terms of the code:

- Why playback and Replay looked right. (What does `dt` look like when `render` is called by the
  player? When Replay seeks back to 0?)
- Why one click on the scrubber left the mark behind, and why Replay did not repair it.
- Why the two `t = 0.6` frames differ.
- Why seeking the same `t` twice in a row passed while every other check failed.

The general lesson: this code's picture at `t` depends on the sequence of `t` values it was
called with before. Playback supplies one friendly sequence (small forward steps), so **a work
that looks right in playback has only been tested on that one sequence.** The tools, the
scrubber, a section export and a reviewer asking "show me 0.6" all supply other sequences.

## 6. Make it move from `t`

Now make `work/first-frame/index.html` move, with one rule: **the mark's position is computed
from `t` alone, and `drawArt` keeps nothing between calls.** Same start (x = 160), same speed
(700 px per second). Write it yourself.

<details>
<summary>After you have written yours: one way to write it</summary>

```js
function drawArt(t) {
  const markX = 160 + 700 * t;            // where the mark is at time t, from t alone
  ctx.fillStyle = INK.blue;
  ctx.beginPath();
  ctx.arc(markX, 540, 90, 0, Math.PI * 2);
  ctx.fill();
}
```
</details>

A quick test you can apply to any `drawArt`: is there a variable outside the function that the
function writes to? Each one is a channel through which one frame can change the next. (The
paper redraw and context reset at the top of `render` exist to close the two channels you did not
write yourself: leftover pixels and leftover context state.)

Repeat the three observations from section 5 on the new version: the scrubber click and Replay
in Firefox; the cold and played-up-to shots of `t = 0.6` (into new folders, say
`$OUT/pure-cold` and `$OUT/pure-played`; `shoot.mjs` never clears a folder); and `verify.mjs`.
The two shots should now be pixel-identical, and `verify.mjs` should end with
`seek is pure in t; contract holds`.

Finally export the frame you would show someone, at a time you choose, twice:

```sh
node still.mjs $PART/work/first-frame/index.html --at 0.6 --out $OUT/first-frame-0.6.png
node still.mjs $PART/work/first-frame/index.html --at 0.6 --out $OUT/first-frame-0.6-again.png
```

Same dimensions, same sha256. One caution when comparing evidence: `still.mjs` and `shoot.mjs`
write PNGs with different encoders, so their file hashes differ even when their pixels agree.
Compare hashes only between runs of the same tool; compare pixels across tools.

## 7. Realtime preview and exact export

You now have two ways to see the film move, and they are not the same kind of thing.

**The player** (`tick` in your file) is a realtime preview. Each browser frame it computes `at`
from the wall clock and draws that time. On a 60 Hz display those times are roughly 1/60 s apart;
on another display they are different times; if one frame is slow, the next one simply draws a
later `t` and the skipped moment is never shown. That is exactly what you want for judging pace
by eye, and exactly what you do not want in a delivered file. The player's Record button captures
this realtime preview to a WebM; it is a convenience, not a delivery.

**`render.mjs`** is the exact export. Read [`tools/render.mjs`](../../../../tools/render.mjs) and
find the loop: for each frame `f` it seeks `from + f / fps`, takes the screenshot, and pipes it to
ffmpeg, however long each frame takes to draw. No frame is dropped or duplicated because no clock
is involved. The repository's brief states the rule plainly: "The MP4 comes from
`tools/render.mjs`, never a realtime screen recording" (`docs/brief.md`, *Deliverable and
contract*).

```sh
node render.mjs $PART/work/first-frame/index.html --engine firefox --out $OUT/first-frame.mp4
FFMPEG=$(node -p "require('ffmpeg-static')")
"$FFMPEG" -hide_banner -i $OUT/first-frame.mp4 -map 0:v:0 -f null - 2>&1 | grep -o 'frame= *[0-9]*' | tail -1
```

`render.mjs` reports 30 frames and notes that the work has no audio (it renders silent); decoding
the MP4 counts 30 frames. Watch the MP4 in a video player.

Now the trap the stateful version sets for export. A full render seeks frames in order from 0,
which is the same friendly sequence playback provides. A section render, which the repository
uses constantly to check one passage without exporting the whole film, starts in the middle:

```sh
node render.mjs $PART/work/stateful/index.html --engine firefox --out $OUT/stateful-full.mp4
node render.mjs $PART/work/stateful/index.html --from 0.5 --to 1 --engine firefox --out $OUT/stateful-from-0.5.mp4
```

Watch both. The full export of the stateful film looks correct. The section covering 0.5–1 s
should start with the mark near the centre (x = 510, where the full export has it at 0.5 s); it
starts near the left edge instead. **An export that looks right does not show that `seek` is pure; it only shows that
this particular seek order happened to work.** The contract check exists because the correct
answer cannot depend on the order of questions.

## 8. Native pixels, not display pixels

Open `work/first-frame/index.html` in Firefox, open the console (Ctrl+Shift+K, or Cmd+Option+K on
a Mac) and evaluate:

```js
[canvas.width, canvas.clientWidth, devicePixelRatio]
```

The canvas has 1080 × 1080 pixels of its own (the **backing store**) but occupies 720 × 720 CSS
pixels on the page. What you see in the browser is the browser resampling 1080 pixels into
`720 × devicePixelRatio` physical pixels of your screen: a preview of the image, not the image.
The tools deal with this in two ways you have already read: `still.mjs` exports the backing
store directly, and the screenshot tools size their virtual screen so that 720 CSS px land on
exactly 1080 device px (`browser.mjs`, `openFilm`). The size itself is a fixed decision:
`docs/brief.md` asks for a "Fixed 1080×1080 backing store at 720 px CSS, independent of DPR, so
halftone pitch stays stable", and `CLAUDE.md` lists it among the invariants.

What does a work lose if its backing store is only as large as its display size? A flat disc is
too coarse a test, so use the supplied probe,
[`project/backing-probe.html`](project/backing-probe.html). Read it: it draws one fixed design (a
grating of 2-px bars on a 5-px pitch, three hairlines, a disc) in 1080 design units, scaled into a
backing store of `BACKING` pixels, always displayed at 720 CSS px. Leave the supplied file at
1080. Make a copy whose backing store equals its CSS size:

```sh
cp $PART/project/backing-probe.html $PART/work/probe-720.html
```

Edit the copy so `const BACKING = 720;`. Then:

```sh
node still.mjs $PART/project/backing-probe.html --at 0 --out $OUT/probe-1080.png
node still.mjs $PART/work/probe-720.html        --at 0 --out $OUT/probe-720.png
node shoot.mjs $PART/work/probe-720.html        --times 0 --size 1080 --engine firefox --out $OUT/probe-720-at-1080
node shoot.mjs $PART/project/backing-probe.html --times 0 --size 540  --engine firefox --out $OUT/probe-1080-at-540
```

`still.mjs` reports what each work really contains: 1080 × 1080 and 720 × 720. The screenshot of
the 720 version is a 1080 × 1080 PNG anyway. Open `probe-1080.png` and
`probe-720-at-1080/t_000.000.png` side by side **at 100% zoom or more, never "fit to window"**,
and compare three regions: the grating (upper left), the hairlines (upper right), the disc's edge.
Record what you see. The `tools/README.md` line for `still.mjs` says it in one sentence:
"`--size` on screenshot tools scales capture, not art." The 1080 capture of a 720 backing store is
an enlargement: the pixel dimensions of a native frame, the information of a 720 one. The
`--size 540` capture of the 1080 probe is the reverse, a reduction. Neither is the work.

The grating is there for a reason. From Part 02 on, tone is made of printed dots a few pixels
apart, and those few pixels are backing-store pixels. A backing store that changes changes the
dots.

One more observation, which will matter in Part 08: on your screen the 1080 grating itself may
show waves or banding that are not in `probe-1080.png`. That is your display resampling 1080
pixels into fewer. Settle pixel questions on the exported PNG at 100%, not on the browser view.

**Optional: the web's usual answer.** Most canvas code sizes the backing store to
`cssWidth × devicePixelRatio`, so it is crisp on every screen. Make another copy with
`const BACKING = Math.round(720 * devicePixelRatio);`, open it in Firefox and check
`canvas.width`; then export it with `still.mjs` (1080, because the tools simulate a device pixel
ratio of 1.5) and with `shoot.mjs --size 2160` (2160). The same file now produces a different
raster on your laptop, on a phone, and for each tool setting. Write down why that is fine for an
interface and wrong for a work whose dots must be the same everywhere.

## 9. Self-contained, and one primary engine

**No network, by construction.** `CLAUDE.md` describes each work as one self-contained
`index.html` that "draws every pixel in Canvas 2D: no libraries, fonts, images or network calls in
the deliverable" (the one exception is recorded instruments embedded in some films' HTML, which
is still inside the file). You read the enforcement in `openFilm`: every non-local request is
aborted and reported. See it happen. Add this line directly under `// ART BEGIN` in
`work/first-frame/index.html`:

```js
new Image().src = 'https://example.com/paper.png';
```

and run `still.mjs` on it. The browser alone would happily fetch the image; the tool refuses to
write a PNG and names the request. Remove the line. Write down two ways a work that loads things
from the network could render differently next year, or on another machine, without anyone
editing its source.

**Firefox is the reference engine.** Two browsers draw the same Canvas calls with slightly
different antialiasing, and their audio differs too; Emergence's record, measuring its score,
notes "Firefox cold renders are byte-identical; Chromium differs by at most two 16-bit steps"
(`films/emergence/FILM.md`). So an exact claim, such as "this PNG is that frame" or "this MP4
matches the checked render", only means something for one named engine. The repository
names Firefox: `docs/brief.md` says "Firefox is primary", `still.mjs` defaults to it, and the
finished films' records describe their delivered MP4s as Firefox renders
(`films/window-seat/FILM.md`, first paragraph). `verify.mjs` checks the contract in **both**
engines, because a work whose seek is impure in either is broken. It reports whether the two
engines' pixels match in a separate line, and does not fail when they don't. So: view, judge and
export in Firefox, and treat Chromium as a second witness to the contract. `shoot.mjs` and
`render.mjs` default to Chromium, which is why the commands above pass `--engine firefox`.

## 11. Decisions you should be able to defend

The repository made three choices you have now seen from the inside. Each is a trade-off, not a
law. In your notes, give for each one a situation where you would choose the alternative.

**Exact `seek(t)` rather than a stateful realtime loop.** The problem is that inspection and
export ask for frames in arbitrary order, and a film is linear media with a fixed duration, so
every frame can be defined as a function of time. You saw the alternative fail: accumulated state
makes the frame at `t` depend on how the program got there. A stateful loop is the better choice
when the state's history *is* the product and nobody needs to jump to an exact moment: a game
responding to its player, an installation reacting to visitors, a simulation explored live. The
repository does not ban simulation, either: Held's kite ropes are simulated, but once, at load, on
a fixed step, and recorded, so that `seek(t)` only reads the recording (`films/held/FILM.md`,
*Motion*, "Chains"). All of that runs before `ready` becomes `true`, which is what `ready` is for.
Part 13 returns to when that trade is worth it.

**One self-contained HTML rather than a modular build.** The problem is reproducibility and
delivery: a work must render the same pixels later, on another machine, offline, with no build
step, and the tools must see exactly what a viewer sees. The price is visible in your own file:
every work carries its own ~1000-line snapshot of the engine, and a later fix to the kit does not
reach works already made. A modular application build (packages, a bundler, shared runtime,
fetched assets) is the better choice when many people maintain one codebase, when many pieces
share a runtime that should update together, or when assets are dynamic, that is, when shared
evolution matters more than a single frozen artifact.

**A fixed 1080 backing store at 720 CSS px rather than a display-sized one.** The problem is that
the image has to be one raster, identical everywhere, at its export resolution, with fine detail
defined in real pixels. You saw both alternatives: a CSS-sized backing store throws away
resolution that no capture can recover; a DPR-scaled one makes the raster depend on the viewer's
screen and the tool's settings. Display-sized or DPR-scaled rendering is the better choice for a
web-only sketch or interface graphics, where crispness on each screen matters and there is no
exact export or pixel-scale texture to protect.
